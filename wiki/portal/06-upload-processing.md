# 06 — Upload intent, upload and processing

**Goal:** the core live-delivery path. A device declares a photo, uploads it to a Worker-signed
URL, and gets it back READY, with three sanitised variants in R2. It must be idempotent, safe
to retry and safe under concurrency, with no queue.

- **Depends on:** 05, and the 01 spike results.
- **Unlocks:** 07, 10, 11, 16.
- **Device check:** n/a.

## Scope
1. **`POST /v1/device/photos`** (device auth, rate-limited per device):
   - Validate with zod: `bytes` ≤ 20 MB, a sha256 hex string, an ISO capture time, a UUID
     `clientPhotoId`, plus `sessionId` and `shot`.
   - The event must be OPEN and not deleted.
   - Use the atomic insert from 03 (photo limit and uniqueness).
     - Existing row, same hash and event: return its state, with READY meaning no upload.
     - Existing row, different hash or event: 409 `conflict`.
     - Over the limit: 409 `photo_limit`.
     - Event closed: 409 `event_closed`.
   - A PENDING result returns an `upload` descriptor: method, URL, headers and `expiresAt`.
2. **`lib/uploadUrl.ts`:**
   - An HMAC-SHA256 (`UPLOAD_KEY`) signature over `photoId|bytes|sha256|exp`. The URL is
     `/v1/device/uploads/{photoId}?exp=&sig=`, valid for 15 minutes.
   - Verification is timing-safe.
3. **`PUT /v1/device/uploads/{photoId}`**, authorised by the signed URL only, with no bearer
   header (so it can later be swapped for presigned R2):
   - Verify the signature and expiry; expired returns 410 `upload_expired`.
   - The photo must exist and be PENDING (READY returns 201 READY, idempotent). Its device must
     not be revoked, and its event must not be deleted.
   - `Content-Length` must equal `bytes`, and the content type must be `image/jpeg`.
   - Stream to `incoming/{photoId}.jpg` with integrity checking, using the approach chosen in
     the spike. A mismatch returns 422 `hash_mismatch`.
   - Call `processPhoto()`, then return 201 READY. If processing hits a transient error, return
     503 with `Retry-After` (the photo stays PENDING). If it runs past the request's time
     budget, return 202 PENDING.
4. **`domain/processPhoto.ts`**, which takes no HTTP types and receives its dependencies:
   - `ImageProcessor` interface: `info()` and `transform(variant)`. The real implementation in
     `lib/images.ts` wraps the `IMAGES` binding.
   - `info` must report JPEG and ≤ the configured megapixels; otherwise mark the photo
     REJECTED with `invalid_image`, delete the incoming object, and return 422.
   - Produce the 3 variants (DESIGN §7 settings, `metadata: none`). Buffer each output, which
     is small, and put it to `events/{eventId}/{photoId}/{variant}.jpg`.
   - Run the conditional `UPDATE … SET state='READY', published_at, width, height,
     variant_bytes WHERE id=? AND state='PENDING' AND event not deleted`. Zero rows changed
     means re-read and return the current state.
   - Delete `incoming/{photoId}.jpg` (best effort).
5. **R2 lifecycle rule** for `incoming/` (1 day): `wrangler r2 bucket lifecycle` commands
   documented in `wiki/Portal.md`, applied in 07.
6. **Tests** (Vitest, real local R2 and D1, fake `ImageProcessor`):
   - Intent: new, duplicate, mismatch, closed, limit; READY short-circuit.
   - Signed URL: tampered photoId, bytes, sha or exp; expired.
   - PUT: wrong length, wrong type, bad hash (if verifiable locally per the spike), revoked
     device, deleted event.
   - Happy path writes 3 variants and sets READY.
   - The same PUT twice gives one READY with identical keys.
   - Two concurrent PUTs give one READY and no error.
   - Failure after the variants are written: still PENDING, and a retry gives READY.
   - Event deleted mid-processing: no READY.
   - REJECTED path.
   - Fixtures in `test/fixtures/`: a tiny real JPEG, a JPEG with GPS EXIF, a PNG renamed
     `.jpg`, a truncated JPEG. Generated by a script, not real guest photos.
